## Background

The old version of [`zep-mcp`](https://github.com/kev-hu/zep-mcp) shipped, served traffic, and lied. Built in early 2025 when I was learning to code, it had a fallback client that returned fake success responses when the Zep API was down — eight tools, two tangled client layers, wrapper scripts for every platform, ~4,000 lines that all *looked* like they were working. A year later I burned it down and rewrote it.

## Problem

The work wasn't refactoring. It was recognizing what to throw out.

A refactor preserves the existing shape and improves it from the inside. That preserves the wrong assumptions. The 2025 version was scaffolded around what I didn't yet know — defensive layers in case the SDK changed under me, fake-success fallback in case I'd misread the failure modes, wrapper scripts in case the install path was wrong. None of those guards earned their keep; they made the code harder to reason about while hiding the failure modes I most needed to see.

The operator move was naming each scaffolding layer for what it actually was — fear-driven complexity from an earlier version of myself — and deleting it rather than improving it. The rewrite ships at ~770 lines (~80% reduction) with 13 tools instead of 8, and no fallback at all. If Zep is down, the server fails loudly. That's the correct behavior; the old "fallback mode that lied to you" was the bug.

## How it shipped

1. **Kept the old git history on purpose.** I didn't `git rm -rf` the old version into a clean repo. Keeping the history means anyone reading the diff can see the contrast directly — what I knew then vs. what I know now is part of the artifact, not embarrassing context to hide. Treating my own learning curve as a public surface is the same logic as the `lessons.md` discipline from `kj-skills`: failures are the most reusable part if you don't bury them.

2. **Re-grouped tools by jobs-to-be-done, not by API endpoint.** The old version had one tool per endpoint — predictable, but it forced the agent to compose primitives every call. The rewrite has 13 tools in two toolsets: **memory** (high-frequency conversational surface — `add_messages`, `get_context`, `search_graph`) and **admin** (lifecycle — user, thread, graph management). `ZEP_TOOLSETS=memory` keeps the production agent surface small; `memory,admin` opens it up for ops sessions. Same separation I'd use for any internal CLI: daily-driver surface small, rarely-needed surface available but out of the way.

3. **Killed the fallback that lied.** The old client wrapped every Zep API call in a try/except that returned `{"status": "ok"}` on any error. That was the worst kind of bug — every test passed and every agent run looked successful, while data dropped silently. The rewrite has no fallback layer. If the API call fails, the tool returns an error and the agent decides what to do. Loud failures are cheaper than quiet ones.

4. **Single entry point, no platform wrappers.** The 2025 version had separate launcher scripts for every install target. The rewrite is a single `server.py` that the MCP client invokes directly. The platform-specific complexity was a guess at what I'd need; MCP standardized that surface, and the right move was deleting my workaround once the standard caught up. Worth naming explicitly: most "infrastructure" code people add is anticipation of problems that the ecosystem solves before the problems arrive.

5. **Use it on my own work first.** I run `zep-mcp` against my own content corpus — video scripts and viewer comments ingested into a Zep knowledge graph. The graph auto-extracts entities and relationships across everything I've published, and I query it for content gaps (entities with rich audience interest but no video yet). Dogfooding kept the API surface honest: every tool that wasn't getting called from my own agent loop got cut from the rewrite.

## What it proved

- **~770 lines, down from ~4,000.** ~80% reduction, with broader API coverage (13 tools vs. 8) and no functionality dropped.
- **11 stars, 5 forks** on a niche infra repo — third-party signal that the rewrite is reusable beyond my own setup.
- **In daily-driver use** for my own content workflow. The eval surface is whether the next video I make comes from a content-gap query that paid off. That metric works.

**Structural insight:** the immune-system pattern (`lessons.md`, post-incident pruning, weekly retros) only earns its keep if you act on it — and the highest-value action is sometimes deleting your own previous work rather than patching it. The 2025 version was a learning artifact; the 2026 rewrite is infrastructure. Naming that boundary explicitly was the work.

## What carries forward

Most internal AI tooling drifts the way the old `zep-mcp` did — scaffolding accretes around early assumptions, fallback layers hide the real failure modes, and the surface area grows because deleting feels riskier than adding. The pattern from this rewrite is general: instrument the failures, name the scaffolding for what it is, and delete it on a cadence. Anywhere AI infrastructure has to survive past the prototype phase — internal agent platforms, eval surfaces, memory layers — the same loop applies. Old code that "worked" is the most expensive code to keep running. The discipline is being willing to write off what you shipped six months ago when the new shape is obvious.

<Drilldown title="What changed in the rewrite">

- **Old shape: two client layers, eight tools, fallback that lied.** Roughly 4,000 lines. The fallback client returned `{"status": "ok"}` on any API error — every test passed; every run looked successful. The two client layers existed because I wasn't sure which API surface I'd want to call from the MCP server, so I left both in case.
- **New shape: one entry point, thirteen tools, no fallback.** Roughly 770 lines. Single `server.py` registers tools directly with FastMCP; no wrapper layer. Tools split into `memory` (high-frequency — `add_messages`, `get_context`, `search_graph`, `add_graph_data`, `get_task`) and `admin` (lifecycle — user, thread, graph, ontology, context-template management). `ZEP_TOOLSETS` env var gates which toolsets register at startup.
- **Why MIT.** Internal tooling that's reusable should be public. The cost of open-sourcing was zero (no proprietary logic, no customer data); the upside was the third-party usage that actually validates whether the design is reusable. 5 forks is the more meaningful signal than 11 stars — forks mean someone wanted to extend it.
- **What I'd still change.** No retry/backoff layer yet — Zep API failures bubble straight up. That's deliberate at the MCP-server layer (the agent should decide), but heavier agent workflows want a thin retry primitive somewhere upstream.
