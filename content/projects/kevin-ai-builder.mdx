## 1. My Build Process

Here's an overview of the steps I take when I am building with teams or customers.

| Step | Principle                    | What it means                                                                                                                                                                                                                                              |
| ---- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 01   | **Measure value first**      | **If you can't articulate why and how much your idea matters, you're not ready to build it yet.**<br/>I've spent time building the wrong thing, so now I apply a stronger filter. If I can't model the [ROI](https://github.com/kev-hu/vapi-voice-agent/blob/main/demo/roi-calculator.md) of an idea, then I don't know enough to start building.
| 02   | **Prototype to communicate** | **Clickable prototypes and artifacts beat PRDs.**<br/>You can prototype UI with ChatGPT, or simulate data schemas with Google Sheets. Create the artifact, then iterate with peers. That's how prototypes become specs.                                                                                       |
| 03   | **Build the crappy version** | **Your MVP is the set of features that answer NO to: "Would this still be useful without it?"**<br/>Early on, auth, reporting, and other infra-ish work can feel like progress without moving the needle. The crappy version keeps you on the real problem. |
| 04   | **Design the loop**          | **Run the cheapest experiment producing a learning signal.**<br/>If no one uses it, you have your answer. If people complain, you have your next feature. The loop helps you see the next decision.                                                                     |
| 05   | **Infrastructure is earned** | **A workaround becomes infrastructure once you've felt the same pain three times.**<br/>It takes discipline to First time it's a one-off, second time it's a coincidence, third time it's a pattern worth promoting. Skip the reps and you risk building infra for problems you don't have.                                                                  |

## 2. Workspace

### Context is Code

 Context is code. It should be versioned, reviewable, and testable. I've come to see the git repo as a shared workspace between humans and agents. A well-structured repo gives agents the context needed to contribute meaningfully. This context lives in the docs, prompts, history, etc. 

Every workspace / repo should have these files:

```text
your-workspace/
├── CLAUDE.md     # repo-specific agent instructions: conventions, setup, what to never do
└── LESSONS.md    # frequent mistakes the agent can't seem to remember
```


### Plugins, Skills, and Slash Commands

This is the actual Claude Code loop I use most often: clarify the intent, turn it into a plan, execute in scoped chunks, review the output, then promote repeated mistakes into context.

- `/brainstorming` — pressure-tests intent before any code is written
- `/writing-plans` — turns a spec into a reviewable, step-by-step plan
- `/subagent-driven-development` — parallelizes execution across independent subagents
- `/lessons` — captures what broke so the same mistake becomes repo context
- `/lessons-prune` — removes stale instructions so the context stays useful

Lessons help your coding agent get smarter each session. 

## 3. Walkthrough: `databank`

`databank` is a local CLI that brokers data from social platforms, RSS feeds, and pretty much any webpage. It scrapes, caches, and cleans data for every downstream repo. I built it after rewriting the same scraping logic across social, news, and job-posting projects too many times. Repeated pain is what makes something infrastructure (Step 5).

```text
~/Code/workspaces/databank/
├── bin/              # CLI entrypoints and analyzers
├── config/           # per-source YAML for each data source
├── data/             # per-source data, read by every downstream repo
│   ├── linkedin/
│   ├── reddit/
│   ├── rss/
│   ├── tiktok/
│   └── youtube/
├── launchd/          # scheduled local jobs
├── logs/             # run history and failures
├── state/            # manifest + cache
├── tests/            # unit and integration tests
├── evals/            # checks and fixtures
├── CLAUDE.md         # agent instructions
├── MEMORY.md         # persistent context
└── LESSONS.md        # costly mistakes
```

### Why CLI?

My CLI tools let me retrieve, analyze, and populate each of the data sources, just by chatting with Claude in the terminal. These features improve the agent experience, too:

- **Progressive disclosure** — `--help` is the contract. The agent reads it before guessing.
- **Self-correcting errors** — failures list valid options and the next command to try.
- **Composable** — pipe into `jq` or another CLI. No glue code.

```text
$ databank yt --help
USAGE: databank yt <action> [options]
  fetch         pull latest videos for a channel
  channels      list configured channels
  stats         summarize a channel's recent performance

$ databank yt fetch --channel @kev
✗ unknown channel: @kev
  did you mean: @kevhudis, @kevhuang
  list all:     databank yt channels
```


## 4. Obsidian as IDE

I use Obsidian because it lets me organize my context easily, and you can prototype clickable  prototyping internal tools quickly. It's local-first, free for commercial use, and you never have to worry about hosting or auth. That's a fast cycle.

- Markdown = filesystem-as-database
- Frontmatter = schema you can query
- Dataview = easy dashboards and UI

You don't need a frontend, a database, or a deploy pipeline to prototype something useful.

![RSS dashboard — 17 feeds, 1,381 articles, classified and summarized by local OSS LLMs](/images/projects/personal-ai-studio-rss-dashboard.png)

17 feeds, 1,381 articles, classified and summarized by local LLMs. The dashboard is one markdown file, and the data is per-source folders.

The query is just a code block that gets evaluated when the page renders:

```javascript
// 2_Dashboards/RSS Dashboard.md
const ROOT      = "/Users/kevinhu/Code/workspaces/databank";
const FEEDS_DIR = `${ROOT}/data/rss/feeds`;
const manifest  = JSON.parse(fs.readFileSync(`${ROOT}/state/manifest.json`));

// Walk per-feed folders, load each articles.json
const all = [];
for (const slug of fs.readdirSync(FEEDS_DIR)) {
  const ap = `${FEEDS_DIR}/${slug}/articles.json`;
  if (fs.existsSync(ap)) all.push(...JSON.parse(fs.readFileSync(ap)));
}

// Banner across the top — catches silent breakage:
//   feeds ok drops      → feed URL changed or 404'd
//   articles flat       → fetcher hasn't run
//   last sweep > 2h     → launchd job died
//   per-article errors  → LLM extraction failed on a post
const feeds   = Object.entries(manifest).filter(([k]) => k.startsWith("rss/feeds/"));
const okFeeds = feeds.filter(([,v]) => v.status === "ok").length;
const errArts = Object.values(manifest).filter(v => v.status === "error").length;
const latest  = Math.max(...feeds.map(([,v]) => Date.parse(v.last_fetched)));
```

You don't need a frontend, a database, or a deploy pipeline to prototype something useful. Obsidian is the fastest path from "I have data" to actually using it.

## 6. Currently Testing

The three things I'm testing right now are all about creating feedback loops between what an agent produces and whether it's actually valuable:

- **Self-improving context loops.** Short-form content is the best testbed for self-improving agents. The feedback signal (views, watch time, completion rate) arrives in hours. Most agentic systems generate but never learn from what shipped. I'm running a faceless TikTok account as the experiment, applying [ACE](https://arxiv.org/abs/2510.04618) (e.g. agents update their own context from outcomes). <br/>**The bet:** the agents that win will be the ones with the tightest, cheapest ground-truth loop.

- **Temporal graph retrieval for relevant context.** It uses vector search and temporal graphs to assemble queryable context. I built [zep-mcp](https://github.com/kev-hu/zep-mcp) to do this. You can surfaces content gaps, e.g. topics frequently mentioned in my comments that I haven't posted about. <br/>**The bet:** This seems like a promising way to extract fresh context from a corpus of data.
