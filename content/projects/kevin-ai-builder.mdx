## Overview

Most of my portfolio is about `WHAT` I've built. This page is about `HOW` I'm building in the AI-era. These are my evolving strategies and practices from projects, customers, and deployments throughout my career. 

## 1. Process

Tools change fast, but pattern recognition accumulates over years of wins and painful lessons. With what I know today, here is my process: 

| Step | Principle                    | What it means                                                                                                                                                                                                                                              |
| ---- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 01   | **Measure value first**      | **If you can't quantify WHY and HOW MUCH it matters, you're not ready to build it.**<br/><br/>Building starts once you know the problem well enough to create an [ROI spreadsheet](https://github.com/kev-hu/vapi-voice-agent/blob/main/demo/roi-calculator.md) that the customer believes.                                               |
| 02   | **Prototype to communicate** | **Versioned HTML prototypes beat PRDs.**<br/><br/>Spin them up with LLMs and mock data — shareable in an email, quick to create, and they convey way more than a spec.                                                                                     |
| 03   | **Build the crappy version** | **Your MVP is the set of features that answer NO to: "would this still be useful without it?"**<br/><br/>Auth, reporting, and other infra-feeling work can feel like progress without moving the needle. The crappy version keeps you on the real problem. |
| 04   | **Design the loop**          | **Run the cheapest experiment that tests whether it actually matters.**<br/><br/>If it doesn't, no one will use it. If it does, people will complain. A good loop is a feedback cycle.                                                                     |
| 05   | **Infrastructure is earned** | **Repeated mistakes and painful workarounds show you what deserves to be infra.**<br/><br/>Skip the reps and you risk building the wrong thing. That's why you need the loop to show you.                                                                  |

## 2. Workspace

### Context

 Context is code. It should be versioned, reviewable, and testable. I've come to see the git repo as a shared workspace between humans and agents. A well-structured repo gives agents the context needed to contribute meaningfully. This context lives in the docs, prompts, history, etc. 

Every workspace / repo should have these three files:

```text
your-workspace/
├── CLAUDE.md     # repo-specific agent instructions: conventions, setup, what to never do
├── MEMORY.md     # non-obvious context not recoverable from code or git history
└── LESSONS.md    # frequent mistakes the agent can't seem to remember
```

### Slash Commands

The tricky part about context engineering is that your context needs to keep up with what's happening: new features, new models, and new launches. 

Slash commands help a lot. I run these after every chat session to manage my context fresh:

- `/lessons` — captures what broke
- `/playbook` — codifies what's working
- `/prune` — removes what you don't need to know

### Plugins 

This is my core building workflow. Plugins scaffold the full lifecycle, and each step produces real artifacts. I shape specs, plans, and tests while reviewing output from the coding agent to ensure nothing drifts. 

- `/brainstorming` — pressure-tests intent before any code is written
- `/writing-plans` — turns a spec into a reviewable, step-by-step plan
- `/subagent-driven-development` — parallelizes execution across independent subagents

## 3. Walkthrough: `databank`

`databank` is a local CLI that brokers data from social platforms, RSS feeds, and pretty much any webpage. It scrapes, caches, and cleans data for every downstream repo.

```text
~/Code/workspaces/databank/
├── bin/              # CLI entrypoints and analyzers
├── config/           # per-source YAML for each data source
├── data/             # per-source data, read by every downstream repo
│   ├── linkedin/
│   ├── reddit/
│   ├── rss/
│   ├── tiktok/
│   └── youtube/
├── launchd/          # scheduled local jobs
├── logs/             # run history and failures
├── state/            # manifest + cache
├── tests/            # unit and integration tests
├── evals/            # checks and fixtures
├── CLAUDE.md         # agent instructions
├── MEMORY.md         # persistent context
└── LESSONS.md        # costly mistakes
```

### Why CLI?

I default to CLIs over MCP servers or APIs. They keep the agent's context window lean — nothing loads until the agent invokes it. Better agent experience, too:

- **Progressive disclosure** — `--help` is the contract. The agent reads it before guessing.
- **Self-correcting errors** — failures list valid options and the next command to try.
- **Composable** — pipe into `jq`, `awk`, or another CLI. No glue code.

```text
$ databank yt --help
USAGE: databank yt <action> [options]
  fetch         pull latest videos for a channel
  channels      list configured channels
  stats         summarize a channel's recent performance

$ databank yt fetch --channel @kev
✗ unknown channel: @kev
  did you mean: @kevhudis, @kevhuang
  list all:     databank yt channels
```


## 4. Obsidian as IDE

Obsidian is less a notes app than an IDE for context, and it's great for prototyping internal tools quickly. It's local-first, free for commercial use, and it runs directly on your computer without hosting or auth.

- Markdown = filesystem-as-database
- Frontmatter = schema you can query
- Dataview = easy dashboards and UI

You don't need a frontend, a database, or a deploy pipeline to prototype something useful.

![RSS dashboard — 17 feeds, 1,381 articles, classified and summarized by local OSS LLMs](/images/projects/personal-ai-studio-rss-dashboard.png)

*17 feeds, 1,381 articles, classified and summarized by local LLMs. The dashboard is one markdown file; the data is per-source folders; the substrate runs the models. No service to keep alive.*

The query is just a code block that gets evaluated when the page renders:

```javascript
// dashboards/jobs/jobs-pipeline.md
const ROOT = "/Users/kevinhu/Code/workspaces/career-camp";
const rawDir = `${ROOT}/job-postings/data/raw`;
const newDir = `${ROOT}/job-postings/data/new`;

const runs = [];
for (let i = 0; i < 30; i++) {
  const date = ymd(daysAgo(i));
  const raw  = tryReadJson(`${rawDir}/${date}.json`);
  const neu  = tryReadJson(`${newDir}/${date}.json`);
  const errs = countErrors(`${rawDir}/${date}-errors.log`);
  runs.push({ date, raw: raw?.length ?? 0, new: neu?.length ?? 0, errors: errs });
}

// Render as a table. Catches silent breakage:
//   raw=0     → scraper or credentials broke
//   new=0     → regex filter broke
//   errors>0  → query timed out
```

You don't need a frontend, a database, or a deploy pipeline to prototype something useful. Obsidian is the fastest path from "I have data" to actually using it.
